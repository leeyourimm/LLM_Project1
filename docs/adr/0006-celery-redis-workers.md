# ADR 0006: Celery + Redis 작업자, 작업 잠금과 OpenDART 호출 한도 공유

- 상태: 채택
- 관련 코드: `src/dartrag/worker/celery_app.py`, `worker/jobs.py`, `src/dartrag/dart/quota.py`

## 맥락
- 새 정기보고서가 올라오면 30분 안에 수집 → 파싱 → 색인 → 변경점 요약 → 알림까지 끝내는 것이 목표다. 웹 요청 안에서 하기에는 무겁고 오래 걸린다.
- OpenDART 는 인증키 하나에 하루 20,000회까지 허용한다. 전체 상장사 과거 데이터 채우기(backfill)가 한도를 다 써서 새 공시 처리가 막히면 안 된다.
- 작업자가 여럿이거나 주기 실행이 겹치면 같은 작업이 두 번 돌 수 있다.
- Redis 는 답변 캐시와 요청 한도에 이미 쓰고 있다.

## 결정
- Celery(브로커·결과 모두 Redis)와 beat 로 주기 작업을 돌린다. 대기열을 셋으로 나눈다: `dart`(OpenDART 를 부르는 작업, 동시에 하나), `process`(파싱·임베딩·요약·평가), `default`(알림, 검증, 정리).
- 작업마다 Redis `SET NX EX` 잠금을 건다. 잠금 값은 작업마다 새 토큰이고, 끝나면 내 토큰일 때만 푼다. 작업자가 죽어도 만료 시간이 지나면 풀린다. 이미 돌고 있으면 건너뛴다.
- 실행 기록은 `job_runs` 에 남겨 `dartrag jobs status` 와 지표로 본다.
- OpenDART 호출 수는 한국 시간 날짜별 Redis 카운터(`DailyQuota`)로 모든 작업자가 함께 세고, 호출 간격도 `SET NX PX` 로 함께 지킨다(`SharedThrottle`). backfill 은 `DART_RESERVE` 만큼을 새 공시 처리 몫으로 남긴다.
- `task_acks_late` 와 `prefetch_multiplier=1` 로 작업자가 죽으면 다른 작업자가 다시 받게 한다. 그래서 작업은 다시 실행해도 결과가 같게(멱등) 짠다.

## 결과와 트레이드오프
- 웹 서버는 가볍게 유지되고, 공시 처리가 작업자 수만큼 늘어난다.
- Redis 가 멈추면 작업 대기열과 잠금, 호출 한도 공유가 모두 멈춘다 (웹 요청 한도는 서버 안 메모리로 대신 세고, 답변 캐시는 건너뛴다).
- 잠금 만료 시간보다 오래 걸리는 작업은 두 번 돌 수 있다. 평가처럼 긴 작업은 잠금 시간을 따로 늘렸다.
- Celery 는 무겁고 설정이 많다. 단계가 더 복잡해지면 Temporal 같은 워크플로 엔진을 검토한다.
